# Эксперимент 002: методика независимой оценки детектора (SYS-233)

Документ описывает стенд `tools/detector_benchmark` и замороженный протокол [data/experiment-002-protocol.json](../data/experiment-002-protocol.json). Результатов здесь нет: отчёт о прогоне пишет Codex после независимой проверки кода и запечатанного запуска. Стенд — offline-эксперимент. Он не подключён к вводу, ничего не заменяет; автоматическое исправление остаётся выключенным независимо от результата.

Код написал Claude; Codex независимо проверяет реализацию, готовит паспорт источников оценки, скачивает данные и выполняет прогон. Автор кода не объявляет изменение одобренным.

## Сборка и тесты

`bin/build`, затем `bin/test` (по очереди `rasklad_tests`, `detector_tests`, `benchmark_tests`). Тесты используют только искусственные данные; единственный читаемый файл репозитория — замороженный протокол, который тест сверяет с ожидаемым документом. Файловые тесты границ `build/` работают во временном каталоге.

## Запуск оценки

```sh
build/tools/detector_benchmark \
    --manifest data/sources.json \
    --en build/experiment-data/en.dic \
    --ru build/experiment-data/ru.dic \
    --eval-manifest data/evaluation-002-sources.json \
    --eval-en build/experiment-002-data/eng.tsv \
    --eval-ru build/experiment-002-data/rus.tsv \
    --protocol data/experiment-002-protocol.json \
    --json > build/experiment-002-report.json
```

Пути к данным даны для примера: стенд принимает любые явно переданные пути и не ищет файлы сам. `--artifact-dir <каталог>` необязателен (см. ниже). Других опций нет; повтор, пустое значение или неизвестная опция — код 2.

Коды выхода: `0` — отчёт выведен; `1` — отказ входных данных; `2` — неверные аргументы; `3` — нарушена целостность (расхождение с экспериментом 001, утечка разделения, сериализация, членство словаря, неполный шум, нестабильная канонизация); `4` — ошибка записи stdout или артефакта. При ненулевом коде stdout пуст: JSON собирается в памяти и печатается только после полного успеха. Сообщения stderr не содержат путей, содержимого файлов, ID и номеров строк.

### Порядок проверок до разбора данных

1. Протокол: обычный файл до 64 KiB, JSON-объект, глубоко равный документу, зашитому в `benchmarkprotocol.cpp`: те же поля, типы, значения, порядок массивов, символы обрезки. Любое изменение файла — отказ с именем поля верхнего уровня. SHA-256 протокола попадает в отчёт.
2. Паспорт словарей `data/sources.json` и словари: проверка эксперимента 001 (статус, scope, `release_approved=false`, точный размер и SHA-256 `.dic`, SHA-256 уведомлений под `data/notices/` с canonical-путями).
3. Паспорт оценки и TSV: размер и SHA-256 каждого файла, SHA-256 уведомлений тем же способом. Корень обоих паспортов (родитель `data/`) должен совпадать.
4. Все четыре SHA-256 источников различны.
5. Если задан `--artifact-dir`, каталог проверяется здесь, до тяжёлой работы.

Только после этого разбираются словари и предложения. Первые метрики вычисляются после проверки всех источников.

## Паспорт данных оценки

`data/evaluation-002-sources.json` пишет Codex. Обязательные поля:

- `schema_version` — целое 1; `status` = `approved-local-evaluation`; `scope` = `local-evaluation-only`; `release_approved` — логическое `false`;
- `evaluation_sources` — ровно два объекта, `en` и `ru`, без повторов. В каждом: `language`, `iso_language` (`eng` для `en`, `rus` для `ru`), `sha256` и `notice_sha256` (64 строчных hex), `bytes` (целое в `[1, 32 MiB]`), `notice` (безопасный путь под `data/notices/`).

Дополнительные описательные поля (URL, лицензия, дата снимка) допускаются и не используются кодом. Уведомления хранятся рядом с данными и производными.

## Подготовка данных и контроль

Данные готовит Codex явным запуском `python3 tools/prepare_cc0_evaluation.py` (скрипт Codex) из отдельно скачанного CC0-only архива. Исходный экспорт Tatoeba содержит четыре столбца `id<TAB>iso<TAB>sentence<TAB>timestamp`; скрипт проверяет технический timestamp и удаляет его, оставляя три столбца формата ниже, и пишет результат только в новый файл внутри `build/`. Сборка и тесты ничего не скачивают и подготовку не запускают. Одобренные данные остаются в игнорируемом `build/` и не коммитятся; после проверки Codex может быть закоммичен только агрегированный отчёт.

Хеши источников и выборки Codex проверяет независимо до просмотра метрик качества. Эталонные значения, независимо вычисленные Codex: SHA-256 модели из одобренных источников `e92e549e5f0853e4cd78d6d997653098b78550eb9911de11421434e26e3985d8`, SHA-256 протокола `4e38458069c2aa0eb884392dc8eda841d2ecf1f27bcb7e2174c87d1e6c1889b8` (см. [предрегистрацию](EXPERIMENT-002-PREREG.md)). Отдельной зашитой константы хеша в стенде нет: протокол сверяется со встроенным документом структурно, по полям и значениям.

## Формат TSV

Распакованный Tatoeba CC0, строгий UTF-8, не больше 32 MiB на файл. Каждая строка — одна запись `id<TAB>iso_language<TAB>sentence`:

- записи разделены `\n`; финальный `\n` необязателен, пустые строки запрещены; `\r` запрещён (CRLF — отказ);
- не больше 250 000 записей на файл (финальный `\n` запись не добавляет). Предел проверяется подсчётом `\n` в сырых байтах до декодирования, `split()`, резервирования и множества ID, чтобы поток переводов строк в пределах 32 MiB не создавал миллионы представлений строк; отказ — `TooManyRecords` без текста. Тот же предел строк записей после заголовка действует для `.dic`. Он выше размера одобренных источников и не меняет их разбор;
- строка не длиннее 8192 байт UTF-8, ровно два символа табуляции;
- ID — 1..18 ASCII-цифр без ведущего нуля, больше нуля, уникален в файле; одинаковые ID в EN и RU — отказ (утечка);
- второй столбец точно равен `iso_language` паспорта;
- предложение непустое, не длиннее 4096 кодовых единиц UTF-16;
- символы категории Cc (NUL, C0, DEL, C1, включая U+0085), кроме разделителей записей и столбцов, запрещены; BOM не снимается и даёт отказ ID.

Любое нарушение — отказ всего запуска. Текст TSV никогда не выводится и не логируется.

## Замороженный метод

### Обучение и точные словари

- Словари эксперимента 001 разбираются его helper'ами. Отфильтрованные списки и число train-типов сверяются с опубликованными значениями эксперимента 001 (`filteredListSha256` и `trainingTypes*`); расхождение — код 3. Повторно выполняется проверка утечек разделения.
- Модель: `NgramModel::train` на ключах `splitForKeys == Train`, алгоритм add-0.5/int8 без изменений, проверка сериализации.
- `exactFull` — все канонические ключи всех одобренных словарных типов; `exactTrain` — только train. Оба хранятся front-coded, сериализуются, загружаются обратно, и для каждого словарного ключа обоих языков членство сверяется с `QSet`.

### Выборка и токенизация

- Точные повторы текста (без нормализации) оставляют запись с наименьшим числовым ID.
- Ранг: `SHA-256("rasklad-SYS-233-holdout-v1" || 0x00 || ASCII-десятичный ID)`, беззнаковое побайтовое сравнение; равные ранги — по меньшему ID.
- Из каждого языка берутся ровно 5000 предложений с наименьшим рангом до любой токенизации; если уникальных меньше — отказ. В отчёт попадают число записей, уникальных текстов, повторов и SHA-256 выбранных ID в порядке ранга (каждый ID и `\n`), но не сами ID.
- Деление по пробельным символам Unicode (`QChar::isSpace`, включая NBSP и типографские пробелы). С краёв снимаются только символы `.!?;:,()[]{}"«»“”„`; внутренняя пунктуация, апостроф, дефис и регистр сохраняются. Пустые после обрезки фрагменты отбрасываются и считаются.
- Фильтрации по модели нет: каждый непустой токен — valid-случай с намерением Keep в родной раскладке языка, включая неподдерживаемые (они учитываются в признаках пригодности и получают Abstain).

### Случаи

- **valid** — естественный токен, намерение Keep. Членство и решения — по каноническим клавишам; исходный регистр сохраняется.
- **wrong** — синтетическая копия только токенов из букв родного языка (en: A–Z/a–z, ru: 33 буквы ru(default)), длиной 1..32, созданная после выборки и токенизации через `convertLayout` с сохранением регистра. Wrong-копия повторно не токенизируется: `k.,jdm` остаётся одним токеном. Восстановлено — Correct и обратное преобразование точно равно исходному токену.
- **ambiguous** — канонический ключ есть в обоих полных словарях. Такие valid и wrong показаны отдельно (`ambiguousValid`, `ambiguousWrong`); любое Correct на них небезопасно и никогда не считается восстановлением.
- Токены короче 4 клавиш и неподдерживаемые получают Abstain во всех методах, кроме `alwaysKeep`.

### Методы и пороги

Пороги фиксированы протоколом, калибровки и подбора на новых данных нет: Single-D `gap=2.5`; two-score `minAlternative=-13`, `maxObserved=-9`, `gap=2.5`.

| Метод | Правило |
| --- | --- |
| `alwaysKeep` | Keep для всех случаев. |
| `exactTrain` | observed train hit → Keep; иначе alternative train hit → Correct; иначе Abstain. |
| `exactFull` | То же по полным словарям. |
| `singleD`, `twoScore` | Решения ядра `decideSingleD`/`decideTwoScore` с замороженными порогами. |
| `exactFullThenTwoScore` | observed full → Keep; иначе alternative full → Correct; иначе `twoScore`. |
| `twoScoreConfirmedByExactFull` | observed full → Keep; иначе Correct, только если `twoScore` = Correct и alternative full; иначе Abstain. |

### Метрики

Для каждого метода — по вхождениям и по уникальным типам (первое вхождение `(язык, роль, канонические клавиши)`, для неподдерживаемых — точный текст):

- valid: Keep, Abstain, ложные изменения и их доля; wrong: восстановлено, неверное преобразование, Keep, Abstain; ambiguous valid/wrong: небезопасные изменения; сумма небезопасных изменений;
- срезы: язык намерения; длина 1–3 и 4+ (клавиши для поддерживаемых, иначе длина UTF-16); членство в полных и отдельно в train-словарях относительно раскладки случая: `unsupported`, `observedOnly`, `alternativeOnly`, `both`, `neither`;
- признаки пригодности токенов по языкам: поддержанные, длина ≥ 4, только буквы, поддержанные с не-буквами, смешанная письменность, неподдерживаемые символы, слишком длинные, с заглавными, неоднозначные, число wrong-копий.

**Аналитическая точность** при доле wrong-layout `p` ∈ {0,1 %, 1 %, 5 %}: `P = p·r / (p·(r+u) + (1−p)·f)`, где `r` — доля восстановленных среди всех wrong (включая неоднозначные), `u` — доля небезопасных изменений среди всех wrong, `f` — доля изменений среди всех valid (включая неоднозначные). Это сценарий при допущении, что смеси представительны и измеренные условные доли `r`, `u`, `f` переносятся на поток с долей `p`; точечное значение — тождество смеси по этим маргинальным долям и независимости токенов не требует. Повторяющиеся слова — не независимые испытания, поэтому доверительный интервал не приводится. Это не измеренная точность в эксплуатации.

**Парные разности** каждого метода против `exactFull` и против `twoScore` на одних и тех же случаях (вхождения и типы): добавленные и потерянные восстановления, добавленные и предотвращённые небезопасные изменения. Прирост восстановлений сообщается только рядом с приростом небезопасных изменений.

## Испытание, не зависящее от корпуса

Все случаи имеют намерение Keep; любое Correct — небезопасное изменение. Отчёт содержит только счётчики по категориям и методам, без токенов.

- Фиксированные искусственные токены (`challengeFixtures`): URL и email только на `example.invalid`, команды, пути, код, хеши, числа, смешанная письменность, имена, аббревиатуры — в us и, где уместно, в ru.
- Шум: по 256 ключей на раскладку длиной 4..16. Попытка `i`: `d = SHA-256("rasklad-SYS-233-noise-v1" || 0x00 || ASCII-десятичный i)`, `i = 0, 1, …`; сначала us, затем ru продолжает счётчик. Длина `4 + d[0] mod 13`, клавиша `j` — `d[1+j] mod 33` (небольшое смещение по модулю). Ключи из любого полного словаря и повторы отбрасываются; всего не больше 100 000 попыток на обе раскладки (ru получает остаток бюджета после us), иначе код 3. Это токены неизвестного намерения, а не доказанные не-слова.
- Все неоднозначные ключи полных словарей длиной ≥ 4, набранные в обеих раскладках.

Эвристические фильтры по результатам испытания не выбираются. Нейросетевые модели и персонализация отложены.

## Точное компактное представление

`FrontCodedLexicon` v1: отсортированные уникальные канонические ключи (байты 0..32, длина 1..32), блоки по 16. Запись — `prefixLen` (u8), `suffixLen` (u8) и байты суффикса; первая запись блока полная. Байт 0 — обычная клавиша, NUL-терминированные строки не используются. Файл: `"RSKF"`, версия, число ключей, размер блока, число блоков, длина нагрузки, `u32` смещения блоков, нагрузка; хвостовых байтов нет. Пара EN/RU — `"RSKP"`, версия, число языков (2), длины частей и сами части.

Загрузка полностью проверяет данные: магию, версию, размер блока, число блоков, нулевое первое и строго растущие смещения в пределах нагрузки, длины записей, `prefixLen` не больше длины предыдущего ключа и равен их общему префиксу, байты клавиш, строгую сортировку, точное заполнение каждого блока и отсутствие хвоста. Поиск — двоичный по декодированным первым ключам блоков, затем последовательное декодирование не более 16 записей и точное сравнение. Вероятностного членства нет.

Это простая экспериментальная структура, а не оптимизированный промышленный FST/DAFSA. `residentStructureBytes` — полезная нагрузка контейнеров (данные, смещения, каталог первых ключей) без накладных расходов аллокатора; это не RSS.

## Задержка

Тёплые измерения в одном потоке на детерминированной выборке: каждый k-й естественный случай, не больше 2000. Перед замером проверяется, что «живой» путь каждого метода даёт то же решение, что и оценка. Один прогрев. `pNN` — nearest-rank перцентиль по случаям от среднего 32 подряд идущих вызовов на одном случае; накладные расходы таймера входят и делятся на 32. Это не задержка одного нажатия. `batchedMeanNs` — один таймер на 32 прохода всей выборки, делённый на число вызовов. Пути решений включают `canonicalizeToken`; отдельно измеряются поиск в front-coded словаре, в `QSet` (справочная хеш-таблица, не компактный формат) и оценка модели по заранее канонизированным ключам.

## Артефакты и проба ресурсов

По умолчанию ничего не пишется. С `--artifact-dir` каталог должен существовать и после разрешения symlink лежать строго внутри `<корень>/build`, причём сам `build/` — не symlink. Через `QSaveFile` записываются только `detector-model.rskn` (`NgramModel::serialize`), `exact-full-lexicons.rskp` (пара полных front-coded словарей) и `artifact-metadata.json` (SHA-256 протокола, паспорта и словарей, пути уведомлений, scope). Существующие symlink и не-обычные файлы не перезаписываются. Текста корпуса в артефактах нет, но точный словарь кодирует каждый словарный ключ и является производной словарей: только локальный эксперимент, распространение не одобрено, уведомления хранятся рядом.

Проба разбирается раньше режима оценки и читает только один артефакт:

```sh
build/tools/detector_benchmark --probe model|exact --artifact <файл> --iterations <0..1000000> --json
```

Она не читает словари, корпуса и train-списки, загружает модель или пару словарей (до 32 MiB), освобождает сырые байты файла и держит только загруженную структуру до выхода. Затем `iterations` раз оценивает или ищет 64 фиксированных синтетических ключа и выводит `readNs`, `deserializeNs`, `loadNs`, `loopNs`, `nsPerOperation`, контрольную сумму, размер и SHA-256 артефакта. `--iterations 0` измеряет загрузку свежего процесса (состояние page cache неизвестно); большие значения дают время внешнему монитору прочитать `/proc` именно процесса пробы, а не супервизора. Сам стенд не запускает процессы и не читает `/proc`. Текущий и пиковый RSS и холодный старт измеряются только снаружи и публикуются с явными границами.

## Гипотезы

Из протокола: H1 — компактная модель добавляет восстановление OOV поверх `exactTrain`/`exactFull`; H2 — `exactFullThenTwoScore` улучшает восстановление относительно `exactFull` без новых небезопасных изменений; H3 — `twoScoreConfirmedByExactFull` уменьшает ложные изменения относительно `exactFull` ценой покрытия; H4 — `twoScore` лучше `singleD` на трудных отрицательных случаях при ненулевом полезном восстановлении. Стенд выводит поля-свидетельства (`hypothesisEvidence`), но вердикт не вычисляет: отчёт о прогоне называет каждую гипотезу подтверждённой, опровергнутой или неопределённой на этой выборке и не утверждает отсутствие ложных исправлений.

## Ограничения

- **Смещение выборки.** Tatoeba CC0 — примеры предложений, отобранные сообществом, а не распределение обычного пользовательского ввода (чаты, код, команды, опечатки).
- **Источники.** Модель и оба точных словаря построены из одних и тех же словарей LibreOffice; корпус оценки независим от них по происхождению. Точные словари не строятся из источника оценки, и слова оценки в них не добавляются; буквальное пересечение ожидаемо и измеряется (срезы членства), но не гарантировано. Расширения по аффиксам нет; оптимизированного FST-базиса нет.
- **Без статистической уверенности.** Повторяющиеся слова — не независимые испытания; доверительные интервалы не заявляются. Типовые метрики показаны рядом с метриками вхождений.
- **Регистр и границы.** Границы токенов взяты из естественного текста до порчи раскладки (oracle-сегментация); wrong-копии сохраняют регистр. Это не сквозная модель сегментации клавиатурного ввода. Неоднозначность определяется только по двум словарям (oracle metadata).
- **Ресурсы.** Размеры структур — не RSS; задержка тёплая; проба измеряет только загрузку и цикл одного артефакта.
- **Публикация.** Публикуются только агрегаты, хеши, размеры и времена. Слова, предложения, ID, пути и сами артефакты не публикуются.
