# INPUT-LAB-004: исправление по Space и порядок keyboard-событий

SYS-223, 2026-11-12. Реализован ограниченный прототип в private compositor fixture и расширен публичный [assertion client](../tests/native_field_client/README.md). Это продолжение [ревизии аналогов](INPUT-BOUNDARY-REVIEW-001.md), не системная установка и не готовый универсальный backend. Чужой код и данные не переносились.

## Что теперь действительно проходит через keyboard

Во всех пяти новых сценариях **всё исходное `ghbdtn `, включая Space, и последующий `x`** идут от отдельного сервера через `wl_keyboard`. Клиент не создаёт для этих символов локальные QKeyEvent и не устанавливает текст поля напрямую. Сервер использует Qt seat `sendKeyEvent` только в своём private compositor, без устройств, uinput или global grab. Клиент подтверждает spontaneous KeyPress X с ненулевым nativeScanCode и независимо сравнивает фактическое поле с константой.

Начальный ввод разрешён только при normal/non-sensitive hints, пустом контексте, курсоре и anchor в нуле. Разделитель завершает фиксированный trigger; существующее чистое ядро `convertLayout` вычисляет замену. Детектор и словари в этом опыте не загружаются: качество распознавания проверялось отдельно, а здесь изолируется доставка правки.

## Реализованный порядок

1. Клиент фокусирует своё normal поле и выдаёт metadata `word_ready`.
2. Сервер доставляет фиксированное слово с пробелом. Клиент проверяет его до исправления.
3. На trailing Space сервер создаёт один план. После 300 мс повторно проверяет snapshot, hints, курсор и выделение. Задержка — условие опыта для воспроизводимости, не требование UX.
4. Перед отправкой клиент через ограниченный `prepare/ready` handshake приостанавливает обработку Wayland-событий. Сервер формирует выбранный порядок keyboard/text-input; клиент возвращается в event loop после `resume`.
5. В варианте с подтверждением сервер держит **один фиксированный ожидающий символ**. Клиент выдаёт `applied` только после чтения реального поля: `привет `, normal focus, без выделения. Лишь затем сервер отправляет X press/release. Это однопозиционный test gate, не готовая универсальная FIFO.
6. В варианте с новым текстом до правки клиент подтверждает реальное `ghbdtn x`. Защищённая ветка возвращает сервер в event loop, получает свежий surrounding state и повторно сверяет snapshot: старый план отменяется, delete/commit не отправляются.

Ожидания handshake ограничены: подготовка/ответы сервера до 500 мс на фазу, чтение команд клиентом до 200/700 мс, максимум 16 байт команды. Служебные строки — фиксированные phase ACK; содержимое полей не передаётся через этот канал. Внутренний deadline 8 с, внешний 10 с. Таймер 50 мс нужен только для планирования проверки fixture: решение зависит от реального совпадения поля/snapshot, а не от истечения таймера.

## Результат пяти сценариев

| Сценарий | Что специально обеспечено | Реальное поле / критерий |
| --- | --- | --- |
| keyboard-after-edit | На wire сначала исправление, затем X | `привет x`, **passed** |
| keyboard-before-edit | В одном накопленном пакете сначала keyboard X, затем исправление | `привет x`, **passed**; Qt observer увидел InputMethod до KeyPress |
| keyboard-acked-edit | X доставлен лишь после `applied` от редактора | `привет x`, **passed**; ACK проверен обеими сторонами |
| keyboard-applied-before-edit | Клиент подтвердил `ghbdtn x`, сервер намеренно применил старый snapshot без обработки нового состояния | `gпривет `, **FAILED: новый ввод потерян** |
| keyboard-guarded-after-key | Тот же уже применённый X; сервер обработал новое состояние и перепроверил старый план | `ghbdtn x`, **passed**; stale refusal 1, replacements 0 |

Отрицательный контроль сохраняет exit 1 клиента и wrapper; процесс завершился штатно. Это провал критерия безопасности, а не успешная замена и не crash. Временная первая версия проверки `keyboard-before-edit` требовала только неизменённого оригинала; её assertion уточнён после наблюдения корректного `привет x`. Этот первый провал не был потерей текста. Финальная таблица основана на независимых конечных сравнениях и явно отличается от отрицательного контроля с подтверждённой потерей X.

Во всех пяти финальных прогонах initial word проверен, native X наблюдался, Password stage не изменён, `protected_text_queries=0`, `replacements_while_protected=0`. Это счётчики нашей policy, не доказательство отсутствия sensitive text внутри Qt compositor. Дополнительно прошли регрессии baseline/focus-race; прежний post-send-race сохранил FAILED. Десять отрицательных проверок окружения/FIFO завершились с кодом 2 до GUI. Сборка клиента и private сервера прошла; production приложение не изменено, его полная тестовая серия заново не запускалась.

Агрегаты и fingerprints: [input-lab-004.json](results/input-lab-004.json). Все новые keyboard-сценарии повторены после добавления начального hints/empty-field gate. Предыдущие регрессии не затронуты этим gate, применяемым только к `keyboard-*`.

## Что стало яснее

- Обычный keyboard-путь действительно отличается от прямой локальной мутации поля из INPUT-LAB-003. В проверенном Qt клиенте порядок на wire не полностью определяет порядок обработки InputMethod/KeyPress внутри приложения.
- Защищённый путь может сохранить текст: либо исправить перед следующим вводом, либо отказаться от опоздавшего исправления после обновления snapshot.
- Проверка на Space полезна и остаётся основной. Но Space сам по себе не резервирует диапазон документа.
- Наличие отрицательного контроля не означает, что будущий контроллер должен выполнять такую последовательность: он специально игнорирует пришедшее новое состояние, чтобы проверить опасность stale mutation.

## Граница применимости

Подтверждение `applied` реализовано **в нашем тестовом редакторе**. Обычный сторонний Qt/GTK/Chromium редактор такого канала нам автоматически не предоставляет. Сервер стенда владеет доставкой синтетических клавиш, а внешний IM-процесс в рабочем Hyprland не получает такую возможность автоматически. `flush` или Wayland roundtrip не подменяют ACK принимающего редактора.

Не проверены arbitrary-length FIFO, переполнение/timeout и восстановление ожидающего пользовательского ввода, mouse/paste/другой writer после ACK, переключение между одинаковыми normal полями, disconnect/crash, held modifiers/repeat, GTK/Chromium/XWayland и реальный input-method-v2 relay. Нельзя считать, что отмена после начала записи эквивалентна откату. Тест с одним ожидающим символом не доказывает надёжность очереди для реального набора.

Следующее решение — установить доступный production механизм упорядочивания/подтверждения или продолжить эксперимент с композиционным IME. Один только клиентский snapshot guard не закрывает гонку после отправки. Рабочий backend остаётся выключен; SYS-223 открыта.

## Происхождение реализации и условия использования

Из XNeur взята архитектурная постановка «обработать границу до дальнейшей пересылки», из WaySwitch — различие отмены до записи и неопределённого исхода после неё. В этом опыте не воспроизводится чужая реализация: нет переноса функций, фрагментов, таблиц, словарей, весов, текстов UI или ресурсов. Источники, commit и лицензии указаны в [ревизии](INPUT-BOUNDARY-REVIEW-001.md). Это не заявление о полной юридической проверке всех будущих зависимостей.

Private сервер продолжает локально использовать уже установленный GPL-3.0-only Qt Wayland Compositor. Его исходник и бинарник остаются в ignored build, в PR и runtime не входят. Публичный клиент использует Qt Core/Gui/Qml/Quick, без линковки с compositor; полная воспроизводимость server из чистого клона не заявляется. Чужие программы не запускались. Закрытый bwrap не даёт доступа к сети, HOME владельца, host display/DBus, GPU или input devices. Настройки системы, права и автозапуск не менялись. Лицензия собственного релиза и данные требуют прежнего отдельного решения; этим опытом они не выбираются.
