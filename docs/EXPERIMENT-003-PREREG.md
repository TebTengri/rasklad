# Предварительный протокол опыта 003: морфологический контроль

SYS-235, 2026-11-11. [JSON протокола](../data/experiment-003-protocol.json) зафиксирован до оценки нового блока. Первый коммит ba8527d, уточнение case-sensitive типов fc2f533 сделано до доступа к исходам нового блока: Hunspell сохраняет case-семантику, поэтому у всех методов тип теперь (язык, роль, точный текст), а не canonical-folded тип опыта 002. Никаких новых порогов или модельных параметров. Claude пишет C++, Codex проверяет данные, код и результаты; реализации не передаётся тестовый текст.

## Новый отложенный блок

Сохраняются файлы Tatoeba CC0 snapshot 2026-11-07 и прежний паспорт, но для каждого языка берём ранги **5000..9999** в прежнем порядке SHA-256(seed + NUL + decimalID) после exact-text dedup с меньшим ID. Первые 5000 предложений относятся к уже просмотренному опыту 002 и исключаются из нового test. IDs и тексты блоков не пересекаются. Отбор фиксирован, исходы нового блока до этой регистрации не вычислялись. Raw snapshot уже находился локально для подготовки и хеширования, это не новый скачанный источник.

Это новый отложенный блок того же источника, не независимый новый жанр. Авторы, темы, шаблоны и написания могут повторяться, документы/леммы не гарантированно независимы. Test 002 после анализа используется только как диагностический. Tokenization и wrong-layout augmentation прежние: границы по исходному тексту, известная раскладка, case-preserving конверсия, >=4 для решений. Нейросеть, дообучение и персонализация не добавляются; пользовательского ввода нет.

## Источники и контроль

Старая модель, train и пороги неизменны. Проверка полного SHA-256 модели обязательна: e92e549e5f0853e4cd78d6d997653098b78550eb9911de11421434e26e3985d8. Полный stem exact остаётся прежним индексом.

Морфологический кандидат — уже установленный Hunspell 1.7.5 через C API spell, с исходными .dic (flags/case сохранены) и pinned .aff LibreOffice той же версии. Нет suggest/analyze/generate, не перечисляются миллионы словоформ. До получения .aff проверены первичные условия: [review](../data/notices/MORPHOLOGY-003-REVIEW.md), [паспорт](../data/morphology-003-sources.json). Библиотека не модифицируется и не распространяется; runtime binary/version/hash фиксируются. Никакой установки пакетов или системной настройки.

Контроль — тот же Hunspell, те же .dic и все остальные .aff bytes, но все строки с первым полем PFX или SFX удалены. Контроль сохраняет case, compounding, NEEDAFFIX и прочие директивы: это **noPfxSfx**, а не отсутствие любой морфологии. Так изолируем эффект именно добавления affix-правил относительно того же движка; отличие raw Hunspell от старого нормализованного stem exact отдельно может включать регистр, состав .dic и compound-семантику.

Всё source/derived data только build/, notices и MODIFICATIONS рядом, release_approved=false. Exact source и подготовка фиксируются SHA-256. До вызова движка проверяются хеши и границы путей; контроль независимо воспроизводится из исходного .aff. Пакет с данными/библиотекой не выпускается.

## Варианты и метки

Девять методов: всегда оставить, stemExact, twoScore, stem→model, modelConfirmedStem, hunspellNoPfxSfx, hunspellFull, morph→model, modelConfirmedMorph. Правила Exact/fallback/confirmation фиксированы в JSON; совпадение observed сохраняет строку, Correct возможен при alt membership и отсутствии observed. Модель/словарь для confirmation должны согласиться. Все решения работают на одном наборе случаев и одном >=4 guard.

Общая метка неоднозначности для всех методов — union stem-both, control-both или fullMorph-both для case-preserving пары. Любое изменение такой пары небезопасно, никогда не считается восстановлением. Отдельно показываем raw число изменений всех valid, включая неоднозначные, чтобы смена меток не скрывала ложные действия. Показываем добавленную движком неоднозначность и membership-срезы.

## Критерии до просмотра результатов

| Гипотеза | Правило оценки |
| --- | --- |
| M1: affix-правила дают покрытие сверх noPfxSfx | Поддержана на выборке при увеличении observed acceptance корректных eligible токенов и числа восстановленных wrong относительно control. Все добавленные/предотвращённые ложные изменения и потери acceptance обязательны; рост покрытия сам по себе не доказывает безопасность |
| M2: полноценный словарь закрывает разрыв с twoScore без дополнительного риска | Строгая поддержка: recovered(fullMorph) >= recovered(twoScore) и unsafe(fullMorph) <= unsafe(twoScore) на общей новой natural выборке. При частичном сокращении разрыва пишем именно частичный результат; показатели hard negatives отдельно |
| M3: модель как подтверждение снижает риск morphFull | Строгая поддержка на natural: unsafe(confirmedMorph) < unsafe(morphFull), с явно указанной потерей recoveries. Если false changes одинаковы, преимущество на natural не доказано; возможный отдельный выигрыш на challenge обозначается отдельно |
| M4: после морфологии остаётся полезный fallback модели | Поддержка покрытия: есть paired addedRecoveries относительно morphFull; одновременно обязательно сообщаем added/prevented unsafe changes. Это не утверждение бесплатной безопасной прибавки |

Для каждого вердикт supported/refuted/inconclusive только на выборке. Occurrences и exact-case unique types; обе стороны преобразования, длины, OOV и acceptance full/control; paired deltas. PPV 0,1%/1%/5% — аналитические сценарии с переносимостью условных частот, не точность эксплуатации. По повторяющимся словам не строим ложную уверенность независимых испытаний.

Те же 645 challenge inputs, fixtures и noise sequence, что в опыте 002. Исключение noise по-прежнему только из старых stem-словарей, а не по новой морфологической приемлемости. Новые фильтры/исключения по результату не подбираются. Новая общая ambiguity-метка допустима по предварительному правилу; inputs не меняются.

## Ресурсы и завершение

Warm latency — реальные вызовы spell и canonicalize, без evaluator cache; отдельно от offline подготовки и агрегирования. Fresh-process probe удерживает только пару full или control Hunspell engines, без корпуса, n-gram model и train-списков. Проверка source .aff/.dic и binary hash входит в загрузку. Измеряем фактический PID процесса через /proc снаружи, current/peak RSS, warm-file-cache/fresh-process start. Размер .aff+.dic и shared library показываем отдельно, не выдаём за RSS и не складываем shared pages как добавочную память системы.

Системный ввод и автоматическое изменение текста остаются выключенными независимо от исхода. Перед любым следующим изменением порогов этот блок становится диагностическим и требуется новый holdout. Исследование завершается воспроизводимым отчётом, тестами, PR и обновлением SYS-235.
