# Компактный локальный детектор ошибочной раскладки

SYS-230, 2026-11-10. Статус: исследовательское предложение, не обученная модель и не готовый детектор. Корпуса, словари и weights не добавлены. Выполнена консультация Claude Opus 5.5 (подтверждённый model ID claude-opus-5-5) и независимая проверка Codex. [Исходное заключение Opus](OPUS_DETECTOR_REVIEW.md) сохранено отдельно; рекомендации ниже учитывают его замечания.

## Постановка

Нужно решить, следует ли заменить уже набранный токен его отображением в другой раскладке. Это не то же самое, что определить алфавит: для каждой последовательности клавиш можно получить кириллицу и латиницу. Generic language ID легко распознает письменность обоих кандидатов, ничего не доказав об исходном намерении.

Различаем три вопроса:

1. Входит ли строка в выбранный конечный словарь? Exact dictionary отвечает только на это.
2. Насколько строка похожа на слова языка? Статистическая модель оценивает это, включая новые/несуществующие слова.
3. Что намеревался написать человек? Без контекста не всегда разрешимо даже при наличии полного словаря. Для коротких форм, имён, аббревиатур и кода нужен исход «не исправлять».

Примеры на вымышленном тексте: ghbdtn/привет — очевидный кандидат для проверки; he/ру и pf/за требуют контекста; ye/ну иллюстрирует столкновение английской формы ye с русской частицей; cat/сфе показывает необходимость сохранять нормальный английский текст. Редкое имя и правдоподобное несуществующее слово не обязаны иметь разный статистический профиль.

## Найденные предшественники

- [Barnes et al., EMNLP 2014](https://aclanthology.org/D14-1068/) используют символьные language-model и словарные признаки для keyboard-layout errors. Их ru→en поисковые запросы и метрики не подтверждают качество нашего двунаправленного desktop-корректора.
- [Lingua](https://github.com/pemistahl/lingua-rs) демонстрирует offline language ID без словаря целых слов. Это опровергает новизну самой идеи «определять язык без словаря», но не решает нашу задачу из коробки.
- [Whichlang](https://github.com/quickwit-oss/whichlang) использует компактную логистическую модель с хешированными признаками. Это ориентир для лёгкого классификатора; опубликованные throughput/accuracy нельзя переносить на короткие ошибочно набранные токены.
- [CLD3](https://github.com/google/cld3) показывает маленькую нейросетевую архитектуру над символьными n-граммами. Для нас нужны отдельные обучение и проверка против script shortcut.
- [kbdlayout](https://github.com/john-psina/kbdlayout) описывает char TextCNN для украинской/английской ошибочной раскладки. Его объявленная accuracy не воспроизведена нами; происхождение корпусов/weights не считается проверенным по одному MIT в README.
- [MySwitcher, описание автора](https://myswitcher.net/en/blog-yak-pratsiuie-avtomatychne-vyznachennia-movy.html) уже объединяет кандидаты раскладок, n-граммы, частоты, контекст и пороги. Это описание продукта, не независимый аудит его кода.

Вывод: нельзя объявлять n-граммы, нейросеть, offline inference или их гибрид изобретением rasklad. Поиск не является патентным исследованием и не доказывает ни мировую новизну, ни свободу использования любого решения.

## Критическая граница: где заканчивается слово

Замечание Opus: обычный текстовый tokenizer ломает wrong-layout слова с пунктуационными клавишами. Например, любовь → k.,jdm, а e.g. → уюпю. Рассматриваем границы в пространстве клавиш с учётом обеих гипотез, явную обработку Shift и отказ на неподдерживаемых символах/неясном сегменте. Пробел может быть первым безопасным триггером исследования, но поведение у пунктуации и конец сегмента ещё требуется определить. Нельзя отдельно идеально распознать слово, если tokenizer его заранее разрезал.

Обработка ё/е в модели не должна терять исходную последовательность клавиш при восстановлении. Нужно сравнить нормализации отдельно и проверить конфликт backtick с кодом. Канонизация клавиш — переименование признаков при известной раскладке, а не источник новой информации или сама по себе причина лучшей точности.

## Кандидаты

| Подход | Что даёт | Главный недостаток | Позиция для эксперимента |
| --- | --- | --- | --- |
| Exact DAFSA/FST/MARISA + необязательная морфология | Точная принадлежность выбранному набору, компактнее наивного списка/хеш-таблицы | Размер зависит от данных; новые формы/имена вне набора; лицензия данных сохраняется | Обязательный baseline, а не автоматически отвергнутый старый метод |
| Quantized n-граммы / variable-order backoff | Дешёвые локальные оценки без списка всех слов | Правдоподобное выдуманное слово получает высокий балл | Первый лёгкий кандидат |
| Hashed linear classifier | Фиксированный бюджет признаков, простой C++ inference | Коллизии, слабая неизвестность, требуется калибровка | Сопоставить с collision-free таблицей |
| Маленькая int8 char CNN/GRU | Нелинейные закономерности и OOV | Данные, runtime и риск уверенного ответа вне распределения | Второй этап, только при измеренном выигрыше |
| Bloom/xor/binary-fuse | Компактный approximate membership | Ложные положительные; не доказательство существования слова | Только предварительный фильтр, не самостоятельное основание замены |
| MPHF | Компактный индекс для известных ключей | Сам по себе не проверяет принадлежность произвольной строки | Нужна отдельная проверка ключа/fingerprint; не называем exact без неё |
| Большая локальная LLM | Более широкий контекст | Размер, RAM, startup, энергия; не гарантирует отсутствие выдумок | Не нужна для первой версии |
| Самостоятельно написанные орфотактические правила | Нет обучения на стороннем корпусе, прозрачный код | Исключения и правдоподобные неслова; не определяют наличие слова | Data-free baseline и защитные признаки, не единственный решатель |

В [MARISA](https://github.com/s-yata/marisa-trie/blob/master/COPYING.md) есть выбор BSD-2-Clause OR LGPL-2.1-or-later для кода. Он не распространяет эти условия на помещённый в trie словарь. Библиотека [binary fuse](https://github.com/FastFilter/xor_singleheader) явно описывает ненулевую вероятность ложных совпадений; fingerprint не заменяет лингвистическое доказательство.

## Гипотеза A: один дифференциальный scorer физических клавиш

Для поддерживаемой пары раскладок преобразуем токен в каноническую последовательность k физических позиций. Это вычисление из явно переданного текста и известной keymap, не чтение raw клавиатуры. Неподдерживаемая keymap или неоднозначная нормализация ведут к отказу.

Вместо двух полных списков слов сравниваем вероятности одного k:

`D(k) = log P(k | RU) - log P(k | EN) + prior`.

Условные вероятности n-грамм с границами слова и backoff можно свести в одну таблицу разностей. Для линейной модели аналогично сохраняется один набор весов бинарного решения, а не два набора и softmax. Оценка выполняется за один проход; реконструировать итоговую строку можно только после допуска.

Экономия имеет цену: одно D не отличает «оба варианта правдоподобны» от «оба бессмысленны, но один немного лучше». Нельзя принимать большую разность за доказательство абсолютной правдоподобности. Нужен независимый показатель отказа: отдельная оценка допустимости/неизвестности, класс reject либо проверенные признаки/малый exact-набор. При изменении языка знак D меняет интерпретацию, но нелинейные пороги, prior и политика отказа не становятся автоматически симметричными.

Обучение можно ставить как contrastive/pairwise задачу: из разрешённого монолингвального текста получать альтернативное отображение тех же клавиш и обучать предпочтение исходного варианта, сохраняя неоднозначные примеры для reject. Это аугментация, не новый свободный корпус: права исходных текстов всё ещё проверяются. Нельзя случайно разнести правильный токен и его wrong-layout копию по train/test и получить завышенную точность.

Возможная инженерная особенность rasklad — проверить такой pair-specific scorer вместе с явным reject-каналом и фиксированным размером, а не обучать многоязычный определитель с сотнями выходов. Полезность этой комбинации — гипотеза для измерения; новизна не установлена.

## Гипотеза B: добавлять точные данные только для трудных решений

Основная модель даёт вероятностный ответ. Малый exact-набор хранит неоднозначные случаи/исключения и запрещает опасные замены. Формировать его только на train/calibration: не вычитывать ошибки закрытого test и не называть полученный результат независимым.

Так можно сосредоточить ограниченный объём данных на предотвращении ложных замен, а не пытаться описать весь язык. Полный сжатый словарь остаётся контрольным вариантом: возможно, он окажется лучше по precision на том же бюджете. Малый набор тоже требует проверенного происхождения.

## Гипотеза C: каскад с tiny-моделью только на неопределённых случаях

Дешёвые правила безопасности и pair scorer обрабатывают простые токены; маленькая квантованная модель исследуется только там, где они воздержались. Нейросеть не получает права обходить ограничения поля/паролей/кода и не обязана принимать решение. При недостатке доказательств результат всего каскада — keep/abstain.

Против аргумента «это всегда быстрее»: каскад добавляет runtime, холодную загрузку и ветвление, а худший случай может запускать оба этапа на каждом слове. Проверять надо весь путь, а не только матрицу весов.

## Дополнение: обучаем не только ответ, но и право воздержаться

Полезная современная линия — selective prediction: оптимизировать coverage при ограниченном риске, а не обычную accuracy принудительного RU/EN ответа. [Geifman & El-Yaniv, 2017](https://arxiv.org/abs/1705.08500) и [Conformal Risk Control, ICLR 2024](https://research.google/pubs/conformal-risk-control/) — источники идей для отдельной калибровки, не готовые гарантии для rasklad.

Калибровка выполняется offline; runtime может хранить только небольшие таблицы порогов по длине/режиму. До применения нужно проверить предпосылки метода и подходящий loss: precision среди отобранных замен не тождественна conformal coverage и не обязана быть монотонной по порогу. Смена домена и зависимые пользовательские токены ограничивают перенос гарантий. Такое дополнение может повысить практическую ценность маленькой модели без большого runtime, но оно тоже не является заявлением мировой новизны.

## Рекомендация после консультации Opus и проверки Codex

Первым исследовать **две оценки правдоподобия с reject-регионом**, рядом с exact-словарём как обязательным baseline. Для длины L хранить/вычислять нормированные оценки S_RU(k) и S_EN(k), например log-probability на единицу длины с учётом BOS/EOS, сглаживания и backoff. Пороги калибруются по длинам; политика должна различать:

- текущий кандидат правдоподобен → keep;
- оба правдоподобны либо оба слабы → abstain;
- альтернативный правдоподобен, текущий слаб и safety gates пройдены → кандидат на замену.

Это более прозрачный первый вариант, чем один D. Разность оценок остаётся абляцией, позволяющей измерить, стоят ли дополнительные 43 KiB второго канала уменьшения ошибок. Абсолютные S тоже не являются доказательством существования слова и требуют теста на неизвестных данных.

Вторая гипотеза Opus — таблица для длины 1–3 на 33 нормализованных позициях букв: 33 + 33² + 33³ = 37 059 последовательностей, по 2 бита → ceil(74 118/8) = 9 265 байт, примерно 9.05 KiB. **Уточнение Codex:** таблица в общем keyspace должна хранить целевые метки RU/EN/ambiguous/unknown, а не безусловные команды переключения: действие зависит от явно известной исходной раскладки. Exact lookup означает точную адресацию, а не истинность или полноту меток. Регистр/Shift, цифры, пунктуация, индексы и упаковка требуют отдельного контракта; пока их нет, неизвестный случай ведёт к отказу.

Таким образом, первая пара для измерения — 2D scorer и тот же scorer с short-table. Оценка данных вместе около 95.3 KiB до служебных структур, **не измеренный размер программы**. Начать можно с полностью abstain short-table, однако это не будет полезным детектором без легитимной и независимой разметки. Сглаживание (простое/backoff или Kneser–Ney) выбирается в эксперименте, не объявляется победителем заранее.

Другие гипотезы Opus: кратковременное накопление численных свидетельств языка серии токенов; небольшой признак окончаний/суффиксов. Первая может ошибаться при code-switching и задерживает решение; контекст нельзя сохранять, публиковать или использовать как dataset, он сбрасывается с полем. Вторая частично дублирует n-граммы с EOS. **Уточнение Codex:** окончание не является exact membership слова — это дополнительный признак правдоподобия, проверяемый абляцией.

## Размер: расчёты, не benchmark

Иллюстративно: 33 физических позиции русских букв плюс BOS/EOS дают алфавит A=35 для выбранной нормализации. Если модель допускает цифры/пунктуацию/другие токены, алфавит и расчёт меняются. Плотные таблицы unigram+bigram+trigram содержат `35 + 35² + 35³ = 44 135` элементов.

- Один int8-канал: 44 135 байт, около 43.1 KiB, плюс заголовки, масштабы и backoff.
- Один int16-канал или два int8-канала: 88 270 байт, около 86.2 KiB, плюс те же накладные расходы.
- Иллюстративная tiny-модель на 30 000 int8 параметров: 30 000 байт weights; это не размер runtime, activations, scales, кода и всего приложения.
- Для сравнения, официальный [fastText lid.176.ftz](https://fasttext.cc/docs/en/language-identification.html) указан как 917 kB, а модель имеет отдельную CC BY-SA 3.0. Малый размер не делает готовые weights автоматически подходящими для нашей задачи или свободными от условий.

Размер exact-словаря нельзя честно назвать без конкретного набора и выбранного кодирования. Квантование может изменить знак/порог; int8 — хранение, не тип накопителя. Длины ограничивать, суммировать в проверенно достаточном int32/int64, отдельно тестировать saturation/overflow и Unicode.

Предварительная цель для эксперимента: данные базового детектора до 256 KiB, без отдельного Python/PyTorch/ONNX runtime в дистрибутиве. Это цель выбора, не обещание качества или текущего результата. Измерять отдельно сжатый пакет, размер на диске, peak/steady RSS, дополнительный размер кода и наличие Qt/других зависимостей.

## Лицензии и данные

Применяется [DATA_POLICY.md](DATA_POLICY.md). У всех рассмотренных методов остаётся вопрос training/eval происхождения. Нельзя заменить непроверенный словарь на статистику того же словаря и объявить проблему решённой.

Первые кандидаты для отдельной проверки: самостоятельно написанные тестовые материалы с ясными правами; конкретные выпуски разрешённых словарей/корпусов с сохранением уведомлений. Пример источников условий: [SCOWL/ESDB](https://github.com/en-wl/wordlist), [ru_RU README](https://github.com/LibreOffice/dictionaries/blob/master/ru_RU/README_ru_RU.txt). Они ещё не допущены в rasklad. Generated-by-LLM не равно автоматически разрешённый и репрезентативный корпус.

## Воспроизводимый эксперимент до выбора победителя

1. Закрыть паспорта данных и разрешённые операции до использования наборов. Собрать train/calibration/test отдельно по источникам и семействам слов; дубликат и его wrong-layout версия не должны попасть в разные части.
2. Первый этап: always-keep, правила, exact-словарь, single-D n-граммы, 2D scorer с reject и 2D + short-table. Всех сравнивать на одной независимой разметке и одинаковой политике поля. Tiny-модель/каскад, контекст и суффиксы — последующие абляции, только если обнаружена остаточная ошибка и есть данные для её проверки.
3. Test включает правильные RU/EN слова, обе ошибочные раскладки, оба допустимых кандидата, имена/OOV, код/CLI, URL, mixed-script, цифры, пунктуацию и типографские символы. Длины 1–2, 3–4 и 5+ оценивать отдельно. Неопределённые намерения размечать как abstain, не навязывать случайную метку.
4. Главные метрики — ложные изменения на корректных токенах и precision предложенных замен при ненулевом coverage. Отдельно recall, abstention, калибровка и обе стороны преобразования. Указать долю реальных ошибок раскладки: на искусственно сбалансированных классах precision не переносится на обычный набор.
5. Пороги выбирать на calibration, закрытый test смотреть после фиксации модели. Для нуля ошибок верхняя 95% оценка порядка 3/N применима лишь к подходящим независимым испытаниям; например 30 000 независимых корректных примеров дают примерно 10⁻⁴, а не доказательство нулевого риска. Повторы одного слова не создают 30 000 независимых случаев.
6. Измерить cold/warm latency p50/p95/p99 и startup на указанном CPU/сборке; сравнить median и хвосты, worst-case длины, allocations и частоту каскадного вызова. Измерить RAM и диск, не выводить их из одного числа параметров.
7. Проверить offline запуск в среде с запрещённой сетью, отсутствие загрузок/таймеров/телеметрии, отсутствие текста в логах и записи на диск. Это отдельные будущие проверки: сейчас детектор отсутствует.
8. Выбирать минимальный вариант, удовлетворяющий согласованным precision/false-correction/coverage и ресурcным ограничениям. Если данных или доказательств мало, оставить ручное исправление; отсутствие мирового новшества не основание усложнять продукт.
